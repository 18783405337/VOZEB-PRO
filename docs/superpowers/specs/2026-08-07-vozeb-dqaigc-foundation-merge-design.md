## 2. 背景与结论

VOZEB-PRO 已具备完整的 AI 运行底座，包括 Agent、图像、视频、音频、Canvas、Generation Worker、Webhook、模型路由、媒体资产、对象存储、积分、订单、支付和作品体系。

DQAIGC 的主要增量价值是：

- 平台、租户、终端用户三级 SaaS 结构
- 域名、子域名、路径等租户识别能力
- 租户 RBAC、应用权限和会员权限
- 应用注册、安装、启停、配置和定价
- 平台成本与租户销售价双层计费
- 租户算力账户、额度包和消耗记录
- 24 个垂直 AI 应用的业务流程、参数、提示词和供应商映射

两个项目技术栈和数据模型差异明显，不能通过目录合并或 PHP 到 TypeScript 的逐行翻译完成整合。目标方案是在 VOZEB-PRO 内增加 SaaS 控制层，并将 DQAIGC 的垂直应用重构为 VOZEB 应用定义和工作流。

## 3. 第一阶段目标

第一阶段交付一个可上线验证的 SaaS MVP：

1. 支持平台、租户、租户成员和终端用户。
2. 支持租户域名解析和严格的数据隔离。
3. 支持平台管理员与租户管理员的独立权限边界。
4. 支持应用注册、安装、启停、配置、权限和租户定价。
5. 支持平台 AI 成本和租户销售收入两套独立账本。
6. 同时支持平台统一收款和租户独立商户收款。
7. 保留 VOZEB 现有 AI Runtime、Worker、模型路由、媒体和支付能力。
8. 迁移三个代表性垂直应用，验证应用框架的通用性。
9. 将现有 VOZEB 数据无损归入默认租户。

### 3.1 非目标

第一阶段不包含：

- 一次性迁移全部 24 个 DQAIGC 应用
- 长期运行 PHP 与 Next.js 两套业务系统
- 自动将 PHP Controller 翻译为 TypeScript
- 开放租户上传任意可执行插件代码
- 为平台代收模式实现自动银行打款或第三方分账
- 完整迁移所有历史生成过程日志
- 重做 VOZEB 已有的 Agent、Canvas、Worker、媒体和作品模块

平台代收模式必须生成准确的租户应结算账本；实际线下或第三方打款可在后续阶段实现。

## 4. 方案选择

### 4.1 选定方案：VOZEB-PRO 原位演进

在 VOZEB-PRO 的 Next.js、PostgreSQL 和 Worker 架构中增加多租户与应用控制层。所有新业务继续遵守现有 Route Handler、server service、repository 和 PostgreSQL 模式。

优点：

- 账户、任务、资产、支付和账本只有一个事实来源
- 复用 VOZEB 已有的异步任务与商业化能力
- 长期部署和维护成本最低
- 可以按功能开关渐进上线

代价：

- 需要对核心资源增加租户边界
- 需要重构现有单用户积分和全局设置模型
- 支付回调、订单和退款需要支持商户归属

### 4.2 未选方案

独立 SaaS 控制中心会引入跨服务鉴权、分布式事务和双重配置，不用于 MVP。

PHP/Next 双系统桥接只允许作为迁移期间的只读数据来源，不允许成为新的写入路径或长期架构。

## 5. 总体架构

系统划分为六个子系统：

1. **Tenant Kernel**：租户、域名、成员、上下文和隔离。
2. **Authorization**：平台角色、租户角色、权限和应用访问控制。
3. **Application Center**：应用定义、版本、安装、配置、工作流和定价。
4. **AI Runtime Adapter**：把应用请求转换为 VOZEB Generation Task。
5. **Billing and Power**：用户销售账本、平台成本账本、算力账户和结算。
6. **Payment Hub**：平台商户、租户商户、订单、回调、退款和对账。

依赖方向如下：

```text
Tenant Kernel
  -> Authorization
  -> Application Center
      -> AI Runtime Adapter
          -> Billing and Power
              -> Payment Hub
```

Payment Hub 负责充值、购买和退款产生的资金事件；AI Runtime 的任务结算不直接依赖某个支付渠道，只依赖钱包和账本。

## 6. Tenant Kernel

### 6.1 身份模型

保留现有 `users` 作为全局身份。一个用户可以加入多个租户，每个租户内具有不同角色和状态。

新增主要实体：

- `tenants`
- `tenant_domains`
- `tenant_members`
- `tenant_roles`
- `tenant_role_permissions`

平台管理员继续属于平台范围，不通过伪造租户成员获得平台权限。

### 6.2 默认租户

数据库迁移时创建固定的默认租户：

- `slug = default`
- 状态为启用
- 归属现有 VOZEB 安装所有者

所有已有用户业务数据回填到默认租户。回填完成前，新代码不得启用强制非空租户约束。迁移顺序为：

1. 创建租户表和可空 `tenant_id`
2. 创建默认租户
3. 分批回填根资源
4. 校验孤立数据和跨表一致性
5. 增加非空、索引、唯一约束和外键

### 6.3 租户解析

公开请求不接受客户端任意传入的 `x-tenant-id`。

解析顺序：

1. 已验证的自定义域名
2. 已配置的平台子域名
3. 开发、预览和后台场景的 `/t/{tenantSlug}` 路径
4. 无租户入口进入默认租户或平台控制台，具体由路由声明决定

内部 Worker 可以使用签名后的内部上下文传递 `tenant_id`。中间件解析得到的租户信息必须在服务端重新校验状态，随后构造不可变 `TenantContext`。

### 6.4 数据隔离

对业务根实体增加 `tenant_id`，首批至少覆盖：

- conversations
- generation_tasks
- assets 和媒体根记录
- canvas projects
- drama projects
- published works
- orders、refunds 和 payment intents
- 用户钱包与积分流水
- 应用使用和计费记录

子记录优先通过父实体外键继承租户边界，避免无意义地修改全部表。

隔离采用三层约束：

1. Route Handler 和 server service 必须持有 `TenantContext`
2. Repository 查询和写入必须包含 `tenant_id`
3. 数据库通过组合唯一索引、外键和非空约束阻止越界数据

高风险账本和商户表可在第二轮加 PostgreSQL RLS；MVP 不依赖 RLS 才能保证正确性。

## 7. Authorization

权限分为两个命名空间：

- 平台权限：租户管理、全局应用发布、平台模型渠道、平台商户、平台账本和审计
- 租户权限：成员、角色、应用安装、应用设置、定价、商户、订单和租户账本

权限键采用稳定字符串，例如：

- `platform.tenants.read`
- `platform.apps.publish`
- `tenant.members.manage`
- `tenant.apps.configure`
- `tenant.billing.read`
- `app.product-image.use`

应用访问需要同时满足：

1. 租户状态有效
2. 成员状态有效
3. 应用已安装且启用
4. 用户具备应用权限
5. 会员或产品权益允许使用
6. 用户和租户余额通过预检查

所有拒绝访问的决策都在服务端执行，前端菜单隐藏只用于改善体验。

## 8. Application Center

### 8.1 应用定义

应用的稳定结构由代码中的 `AppDefinition` 表达，数据库保存发布版本和租户可变配置。建议定义包含：

- `key`
- `version`
- `name`
- `category`
- `capabilities`
- `permissions`
- `inputSchema`
- `outputSchema`
- `workflowKey`
- `billingMetric`
- `defaultPricing`
- `renderer`

应用定义必须版本化。正在运行的任务保存应用版本和价格快照，后续修改应用配置不能改变历史账单。

### 8.2 安装和配置

数据库新增：

- `apps`
- `app_versions`
- `tenant_apps`
- `tenant_app_settings`
- `tenant_app_pricing`

平台负责发布可用应用版本。租户可以安装、启停、选择允许版本、配置模型、配置业务参数和设置终端售价。

配置解析顺序：

```text
平台默认配置
  -> 租户覆盖配置
  -> 应用安装配置
  -> 本次请求允许覆盖的参数
```

敏感配置不能出现在浏览器返回值中。

### 8.3 UI 策略

简单应用使用基于 schema 的通用表单和结果页。复杂应用允许注册专用 React renderer，但仍使用统一的权限、任务、资产和计费接口。

不得为了追求动态化而把所有页面强制放入通用表单。以下类型使用专用页面：

- 多步骤商品套图
- 视频时间线和智能混剪
- 数字人驱动
- 需要 Canvas 交互的应用

### 8.4 首批试点应用

1. **背景移除**：验证单输入、单任务和固定计费。
2. **商品图**：验证模板、租户配置、参考图和差异化售价。
3. **商品宣传视频**：验证图像到视频的多步骤异步工作流、部分失败和组合结算。

试点完成后，应用框架必须能够覆盖其余应用的大多数共同能力，再进入批量迁移。

## 9. AI Runtime Adapter

应用层不能直接调用供应商 API。所有生成统一转换为 VOZEB Generation Task。

提交链路：

1. 解析 TenantContext 和用户身份
2. 校验应用安装、权限和权益
3. 解析应用版本、模型渠道和配置
4. 计算用户销售价与平台预估成本
5. 预占用户余额和租户算力
6. 创建带价格快照的 Generation Task
7. Worker 调用模型供应商
8. 结果持久化到租户资产
9. 结算实际成本和销售流水
10. 失败时释放预占或执行差额退款

任务快照至少保存：

- `tenant_id`
- `app_key` 和 `app_version`
- `workflow_key`
- `model_channel_id`
- 输入参数摘要
- 租户销售价快照
- 平台成本规则快照
- `collection_mode`
- 创建者和幂等键

Worker 不依赖当前租户配置重新计算历史任务。

## 10. Billing and Power

### 10.1 账本拆分

现有用户积分不能同时表达平台成本与租户销售收入。新增或重构为三个独立账户域：

1. **Tenant User Wallet**：终端用户在某租户内的余额、积分或权益。
2. **Tenant Power Account**：租户向平台购买的 AI 算力和额度包。
3. **Tenant Settlement Account**：平台代收模式下租户应收、退款和已结算金额。

账本记录不可原地修改。冲正通过新增反向记录完成。

### 10.2 双层结算

每个成功任务至少生成：

- 一条用户销售流水：用户按租户售价消费
- 一条平台成本流水：租户按平台成本规则消耗算力

两者金额可以不同，币种和积分单位必须在价格快照中明确。平台毛利、租户毛利和供应商成本不能通过同一个字段推导。

### 10.3 预占和结算状态

统一状态：

- `reserved`
- `settled`
- `released`
- `reversed`

同一任务、账户和账本类型只能有一个有效预占。结算接口使用 `generation_task_id + ledger_type` 作为幂等边界。

任务部分成功时，由工作流定义可计费步骤。未执行或失败步骤必须释放对应预占。

## 11. Payment Hub

### 11.1 商户账户

新增 `merchant_accounts`，核心字段包括：

- 所有者类型：`platform` 或 `tenant`
- 所有者 ID
- 支付渠道
- 状态
- 加密后的渠道配置
- Webhook 识别信息
- 测试和生产环境标记

商户密钥使用服务端主密钥加密保存，日志、前端和错误响应不得输出明文。

### 11.2 两种收款模式

订单保存：

- `tenant_id`
- `collection_mode`
- `merchant_account_id`
- `beneficiary_type`
- 商品和价格快照
- 平台成本金额
- 租户销售金额

**平台统一收款**

- 终端用户向平台商户支付
- 用户钱包或权益到账
- 系统记录租户应结算金额
- 退款同时冲正用户权益和租户应结算账本

**租户独立收款**

- 终端用户直接向租户商户支付
- 平台验证回调后记录用户权益到账
- 资金不进入平台结算账户
- AI 使用仍从租户算力账户扣除平台成本

### 11.3 Webhook 路由

Webhook 先通过渠道标识和商户识别信息确定 `merchant_account_id`，再确定租户。不得依赖请求体中的租户 ID。

回调处理必须：

- 验签
- 防重放
- 幂等
- 校验金额、币种、订单和商户归属
- 保存原始事件摘要
- 支持失败重试和人工复核

现有支付渠道继续复用各自适配器，租户差异通过商户账户上下文注入。

## 12. 模型渠道与配置

模型渠道采用三级结构：

1. 平台发布逻辑模型和默认渠道
2. 租户选择平台渠道或配置租户自有渠道
3. 应用安装选择允许使用的逻辑模型

租户自有供应商密钥存入租户密钥空间。Generation Task 保存实际渠道快照，但面向终端用户的接口不得泄露供应商、成本价和内部提示词。

## 13. API 和错误处理

新增接口统一返回：

```json
{
  "code": "tenant.apps.not_installed",
  "data": null,
  "msg": "应用未安装"
}
```

并使用符合语义的 HTTP 状态码。

核心错误码至少覆盖：

- 租户不存在、停用或域名未验证
- 用户不是租户成员
- 权限不足
- 应用未安装、停用或版本不可用
- 用户余额不足
- 租户算力不足
- 商户不可用
- 支付回调验签失败
- 任务重复提交
- 结算需要人工复核

业务错误不得回退为无信息的 500。供应商原始错误和内部提示词不得返回客户端。

## 14. 数据迁移

迁移采用“导出、转换、导入、校验”模式，不允许 VOZEB 在运行时直接查询 DQAIGC 的 MySQL 作为业务依赖。

迁移批次：

1. 租户、域名和管理员
2. 用户与租户成员关系
3. 应用安装、配置、权限和价格
4. 租户算力余额与可审计流水
5. 商户配置，经重新加密后导入
6. 必要的历史订单和资产索引

历史生成记录默认迁移元数据和资产引用，不迁移全部轮询日志。所有迁移工具支持 dry-run、断点续跑和幂等导入。

上线采用：

1. VOZEB 默认租户回填
2. 内部测试租户
3. 新租户先进入 VOZEB
4. 选定一个低风险线上租户灰度迁移
5. 扩大迁移批次
6. DQAIGC 进入只读
7. 完成核对后停止旧写入服务

## 15. 可观测性和审计

日志和追踪字段统一包含：

- `request_id`
- `tenant_id`
- `user_id`
- `app_key`
- `generation_task_id`
- `order_id`
- `merchant_account_id`

平台操作、租户管理操作、价格变化、商户配置变化和人工账本调整必须产生审计事件。

监控至少包含：

- 按租户统计的任务成功率和耗时
- Worker backlog 和 lease 异常
- 预占长时间未结算
- Webhook 失败和重复事件
- 账本余额与订单对账差异
- 跨租户访问拒绝事件

## 16. 安全要求

- 所有租户归属由服务端确定
- Repository 禁止提供无租户条件的通用业务查询
- 平台管理员接口与租户管理员接口分离
- 商户和供应商密钥加密保存并支持轮换
- Webhook 必须验签和防重放
- 资产下载和引用校验租户归属
- 导出、备份和恢复必须携带租户边界
- 测试环境不得连接生产商户或生产供应商密钥

## 17. 测试策略

### 17.1 单元测试

- 租户解析优先级
- 权限计算
- 应用配置合并
- 价格快照
- 预占、结算、释放和冲正
- Webhook 商户识别和验签

### 17.2 Repository 集成测试

每个租户化 Repository 至少包含：

- 同租户正常读写
- 另一租户无法读取
- 另一租户无法更新和删除
- 重复键不会跨租户冲突
- 父子资源不能跨租户关联

### 17.3 业务集成测试

- 应用安装到任务完成的完整链路
- 用户余额不足
- 租户算力不足
- 任务失败释放双侧预占
- 平台统一收款、退款和租户应结算冲正
- 租户独立收款、退款和平台成本扣除
- Worker 重试不会重复扣费

### 17.4 E2E

- 平台创建租户和发布应用
- 租户配置域名、成员、角色和应用
- 终端用户购买并使用试点应用
- 两个浏览器上下文验证跨租户隔离
- 平台和租户管理员不能进入对方权限域

## 18. 实施阶段与依赖

### 阶段 0：架构基线与迁移准备

- 固化数据字典和表级租户归属
- 建立当前测试和性能基线
- 确定默认租户回填脚本
- 建立功能开关和迁移审计表

### 阶段 2：Authorization 与后台

- 平台和租户权限命名空间
- 租户角色和成员管理
- 平台、租户后台导航与访问控制

预计 3 至 4 周。

### 阶段 3：Application Center

- AppDefinition 和版本
- 安装、启停、配置、权限和定价
- 通用应用入口和专用 renderer 接口

预计 2 至 3 周。

### 阶段 4：Billing、Power 与 Payment Hub

- 三类账户和双层账本
- 预占、结算、释放、冲正
- 平台商户和租户商户
- 双收款模式、退款和对账

预计 4 至 5 周。

### 阶段 5：试点应用

- 背景移除
- 商品图
- 商品宣传视频

预计 3 至 4 周。

### 阶段 6：迁移和上线

- DQAIGC 数据导入工具
- 灰度迁移
- 安全、性能和灾备验证
- 旧系统只读切换

预计 2 至 3 周。

整体 MVP 预计 16 至 21 周。该估算假设 3 至 5 人并行参与，至少包含后端/全栈、前端和测试能力。双收款模式是最大不确定项，应在阶段 4 开始前使用真实支付沙箱完成技术验证。

## 19. 验收标准

MVP 完成必须同时满足：

1. 两个租户使用相同用户和相同应用时，任务、资产、订单和账本完全隔离。
2. 现有 VOZEB 数据全部归入默认租户，核心功能回归通过。
3. 平台可发布应用，租户可安装、启停、授权、配置和定价。
4. 三个试点应用均通过统一 Generation Task 和 Worker 执行。
5. 每个成功任务产生可审计的用户销售流水和平台成本流水。
6. Worker 重试、Webhook 重放和重复请求不会重复扣费。
7. 平台商户和租户商户都能完成支付、退款和对账。
8. 商户密钥和供应商密钥不会出现在前端、日志或普通错误响应中。
9. 跨租户负向测试、支付集成测试和核心 E2E 全部通过。
10. DQAIGC 线上租户可通过可重复执行的迁移工具完成灰度导入。

## 20. 后续应用迁移顺序

MVP 后按以下顺序迁移剩余应用：

1. 配置型单任务应用：修复、扩图、风格迁移、翻译、局部重绘等。
2. 组合型图像应用：模特换装、发型、人物替换、商品多角度等。
3. 多步骤工作流：商品套图、宣传视频、智能混剪。
4. 专项供应商集成：数字人、动作迁移、image_human。

每一批应用单独形成设计、实施计划和验收清单，不能以“兼容全部应用”为理由扩大基础框架。
